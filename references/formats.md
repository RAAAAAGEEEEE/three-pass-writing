# Format profiles

Pick one and paste it into the pass 1 and pass 2 prompts. For cold email, DM, or any first-contact message, use `cold-outreach.md` instead.

Lengths are targets, not suggestions: over target is a P1 finding.

---

## Social post (X, LinkedIn, Bluesky)

**Target** 40–120 words. X: under 280 characters unless the user asks for a thread.
**Structure** Line 1 carries the whole idea. Lines 2–4 give the concrete detail. Last line asks one thing or lands one point.

What matters: the first line is read out of context, in a feed, by someone who does not know the product. It must work alone.

Rules
- One idea per post. A second idea makes a second post.
- A specific number, name, or moment beats a general claim every time.
- No hashtag walls: two at most, and only if the user's samples use them.
- Threads: one idea per item, each readable standalone, first item strong enough to earn the rest.
- No engagement bait the user has not asked for ("agree?", "thoughts?" as reflex).

Failure modes: sounding like an announcement when it should sound like a person; burying the point under setup; a hook the body does not deliver on.

## Landing page copy

**Target** Hero: headline under 12 words, subhead under 25. Section: 30–80 words.
**Structure** Headline (what it does, for whom) → subhead (how, or the proof) → one CTA → sections that each answer one objection.

Rules
- The headline says what the product does. Cleverness that costs clarity is a P1.
- Every section earns its place by answering an objection from the writing context.
- Social proof only if it exists and is quotable. Empty placeholders are worse than no section.
- One primary CTA per page; a secondary is a link, not a button competing with it.
- Feature lists say what the user gets, not what the code contains.

## Changelog / release note

**Target** 20–60 words per entry.
**Structure** What changed → who it affects → what to do about it.

Rules
- Lead with the user-visible change, not the internal refactor.
- Breaking changes first, marked as breaking, with the migration path.
- Version and date explicit. "Recently" is not a date.
- No "various improvements and bug fixes" as a standalone entry.
- Anything not merged is not in the changelog.

## Product announcement

**Target** 100–200 words.
**Structure** What is now possible → why it matters to this reader → how to start → one link.

Rules
- Open with the capability, not the journey ("we're excited to announce").
- One concrete example beats the full feature list.
- Say what it does not do yet if the omission is the obvious next question.
- Availability is explicit: all plans, paid only, beta, waitlist.

---

## Documentation page

**Target** As long as the task needs, no longer.
**Structure** What this page gets you → prerequisites → steps → verification → what to do when it fails.

Rules
- Second person, imperative, present tense.
- Every command copy-pasteable as written, and actually run before being documented.
- Every path verified to exist.
- Show the expected output so the reader can tell success from silence.
- Failure modes documented, not hidden.
- Jargon defined at first use.

---

## Support reply

**Target** 40–120 words.
**Structure** Answer first → the why in one line → the next step → an open door.

Rules
- Answer in the first sentence, even when the answer is no.
- No blame, no defensiveness, no unearned apology stacking.
- Do not promise a fix, a date, or a refund the user has not authorised; flag it as an open decision instead.
- If it is a bug, say so plainly and say what happens next.

---

## App store description

**Target** First 3 lines carry the decision; 80–150 words total.
**Structure** What it does → who for → three concrete capabilities → what it costs.

Rules
- No keyword stuffing.
- No claim the store listing cannot back: rankings, awards, user counts.
- Pricing and subscription terms stated where the store requires it.
- Screenshots' captions count as copy: write them.

---

## Anything else

Ask the user for one example of the format done well, derive the structure and the length target from it, and note the profile in the writing context so the next piece reuses it.
